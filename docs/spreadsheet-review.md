# Review of オブジェクト定義書.xlsx (database definition)

A comparison of the Excel table definitions with the screen specs (詳細設計書) and PostgreSQL. Every problem below is already fixed in the database schema (`prisma/migrations/0_init/migration.sql`, formerly `db/schema.sql`). The "Fix" column says how.

## A. Will not work in PostgreSQL

The sheet uses Microsoft SQL Server types. PostgreSQL either lacks them or they behave differently.

| # | In the sheet | Problem | Fix |
|---|---|---|---|
| A1 | `nchar`, `nvarchar` | SQL Server types. In PostgreSQL every text column already handles Japanese and Bengali. | `varchar(n)` or `text` |
| A2 | `char(n)` for names, emails, URLs | `char` pads with spaces to the full length, so `'abc@x.jp'` is stored as `'abc@x.jp      …'`, and comparisons and the app have to trim it. | `varchar(n)`. `char` is kept only for the fixed 12-digit member number. |
| A3 | `bit` for Yes/No flags | Not a yes/no type in PostgreSQL. | `boolean` (true / false) |
| A4 | `image` for 写真, ロゴ | Type doesn't exist. Storing pictures and videos inside the database also makes it huge and slow. | Files go to file storage (S3); the database keeps only the file key (`photo_key`, `logo_key`). |
| A5 | `money` for 給与 | Locale-dependent formatting, and awkward to calculate with. | `integer` yen |
| A6 | `numeric(4)` "3v1" for 身長・体重, `numeric(3)` "9.9" for 視力 | Without a scale, PostgreSQL stores whole numbers only, so `170.5` becomes `171` and `1.2` becomes `1`. | `numeric(4,1)` and `numeric(3,1)` |
| A7 | 勤務時間 / 1日の労働時間 as `nchar(5)` "hh:mm" | Text can't be validated or used for calculations, so `"25:99"` would be accepted. | `time` |

## B. Contradictions between the sheet and the screen specs

| # | Problem | Where | Fix |
|---|---|---|---|
| B1 | **Year/month dropdown codes clash.** The master defines `12` = 給与, `13` = 特定試験, `16` = 年, `17` = 月. But the education, work, certification and visa screens load "12(年)" and "13(月)", so they would show salary ranges and exam statuses as years and months. | 選択項目マスタ vs BHALO013, 015, 016, 017 | Years and months are generated by the app, not stored. Each list has a name (`category`) instead of a number. |
| B2 | ログインマスタ: the sheet makes ログインID (char 50) the primary key. BHALO001 instead adds a 連番 char(20) key. ユーザマスタ's ログインID is char 80. Three different definitions of a login ID. | ログインマスタ, ユーザマスタ, BHALO001 転送 | One `users` table with `email varchar(254)` unique and a separate `id`. |
| B3 | 特定技能試験 lists 合格・受験中・未受験, but BHALO022 shows only 合格・未受験. | 特定技能, BHALO022 | Kept all three (`passed`, `in_progress`, `not_taken`). |
| B4 | The resume (履歴書) prints **フリガナ**, but no table has a furigana column for individuals. | 履歴書 layout vs 個人会員情報 | Added `individuals.name_kana`. |
| B5 | 求人情報 has 特記事項, but the screens and the job order (求人票) call it **会社の特長**. | 求人情報, BHALO116, 117, 802 | Named `features` (会社の特長). |
| B6 | 求人票 repeats 種別 (job type) already stored in 求人情報. If one is edited, they disagree. | 求人票 | `job_orders` has only its own fields and links to `job_postings`. |
| B7 | 法人種別 holds one value (企業 or 学校), but BHALO110 lets an organisation tick both company and school types. | 法人会員情報 vs BHALO110 | `kind` + six yes/no flags, with a rule that at least one is ticked. |
| B8 | 生徒募集 学費 is text `nchar(100)`, but the screen enters yen. | 生徒募集情報 vs BHALO156 | `annual_tuition integer` (yen per year) |
| B9 | 従業員数・生徒数 is text `nchar(6)`. | 法人会員情報 | `integer` |
| B10 | 在留希望年数 is text `char(2)`. | 技人国 / 特定技能 / 技能実習 | `smallint` from 0 to 99 |
| B11 | 人気業種: the Japanese name is `char(12)`, a non-Unicode type in SQL Server that can break Japanese text, and the English name is `nchar(120)`. The two types look swapped. | 人気業種 | `label_ja varchar(60)`, `label_en varchar(120)` |
| B12 | The 管理マスタ sheet's title says **人気業種** (copied from the previous sheet). | 管理マスタ | — |
| B13 | Copy-paste notes: 血液型 and 家族 生年月日 are described as "hh:mm形式". The salary list is described as loading 利き手 (dominant hand) data. | BHALO201, 202, 200 | — |
| B14 | 採番マスタ counters are `int`, but every 連番 key is `char(8)` "00000000". | 採番マスタ vs all child tables | Numeric `id` generated by the database. |

## C. Design problems

| # | Problem | Why it matters | Fix |
|---|---|---|---|
| C1 | **No relationships are defined.** The 外部ID column is empty everywhere; tables are only "linked" by having the same 会員番号 value. | Nothing stops orphan rows, such as languages for a deleted member, or a job for a company that doesn't exist. | 21 real foreign keys with delete rules. |
| C2 | **Passwords stored as `char(30)`.** That means plain text. | If the database leaks, every password leaks. Admin screens BHALO811 and 813 even display passwords. | Passwords are hashed by the login library and never shown. |
| C3 | 採番マスタ: read the counter, add 1, write it back. | Two people signing up at the same moment can get the **same member number**. | PostgreSQL sequences, which are safe under load. |
| C4 | 求人番号 and 生徒募集番号 are `int(2)`. | A company can never have more than 99 job postings. | `integer`, unique per company |
| C5 | ログインマスタ has no 非アクティブFLG. | A deactivated member can still log in. | `users.is_active` |
| C6 | No email verification field. | Anyone can register with someone else's email. | `users.email_verified` |
| C7 | Contact requests (コンタクト申込) are only sent by email. | Staff can't see the history, track status, or count requests per company. | `applications` + `application_items` tables |
| C8 | Dropdown master has only one name per item. | The site is in Japanese, English and Bengali. | `label_ja`, `label_en`, `label_bn` |
| C9 | Child tables have one 登録・更新日 `date`. | You can't tell when a row was created versus last changed, or at what time. | `created_at` and `updated_at` as `timestamptz` |
| C10 | パスポート and 宗教 stored with no protection. | 宗教 is 要配慮個人情報 (sensitive personal information under Japan's privacy law, APPI) and needs explicit consent. A passport number is high-risk if leaked. | Passport encrypted by the app. Added `resumes.sensitive_consent_at`. Added `audit_logs` for staff access. |
| C11 | VISA expiry split into two `int` columns (year, month). | Harder to search, e.g. "visas expiring in 3 months". | One `date` (1st of the month) |
| C12 | The ER sheet (サイトマップ&ER図) lists tables like 学部情報 and fields like 企業名イニシャル that aren't in オブジェクト定義書. | Two sources that disagree. | `prisma/schema.prisma` and its migrations are now the single source; the Excel should be updated or retired. |

## D. Admin screen specs (詳細設計書 BHALO800–816)

Found while building the admin console (2026-10-15). The console implements the corrected behaviour in the right-hand column; the Excel files themselves are unchanged.

|---|---|---|---|
| D1 | BHALO803, 805, 807, 810, 813: MSG0001 = 「この求人情報を削除します。よろしいですか？」 | Copied from 801; these screens delete companies, members, schools, users and logins, not jobs. | Each screen names its own data: 企業情報 / 個人会員情報 / 学校情報 / ユーザ / ログイン情報と関連する会員情報. |
| D2 | BHALO803 and 807: 業種・所在地・URL・学校種別 "求人情報より表示"; 809: 非アクティブ "求人情報の非アクティブFLG" | Those columns belong to 法人会員情報 (803/807) and 生徒募集情報 (809). | Read from the correct table. |
| D3 | BHALO805 明細表示 "抽出された求人情報を表示する"; BHALO813 "抽出された学校情報を表示する" | Copy-paste; the lists show members and logins. | — |
| D4 | BHALO806: 新規追加・編集処理 "法人会員番号が設定されている場合"; 専門学校希望選択＝"0"(希望); sheet named BHALO0806F. BHALO811: "法人会員番号が設定されている場合" | The member screen uses 個人会員番号; 専門学校希望 is "1" like the other five flags; 811 keys on the edited ログインID. | Corrected. |
| D5 | BHALO811 and 813 display パスワード from the master | Passwords stored and shown in plain text; anyone with admin access could read every member's password. | Passwords are hashed (scrypt) and never displayed. 811 sets a new password; 813 shows login state only. |
| D6 | BHALO800 最近登録した求人情報: read 法人会員情報 (法人種別＝企業) by 登録日 and show its first job; clicking the 連番 opens 新規企業追加・編集画面. 希望種別 shows only the first checked wish. | A company with three jobs would show one row, and the newest *job* might belong to an old company. The link target doesn't match the column. | The 20 newest 求人情報, one row per job, linking to the job's edit screen. 希望種別 shows every checked wish. |
| D7 | BHALO814 採番マスタ: read the counter, add 1, write it back; counters for every child table | Two registrations at the same moment get the same number (C3). | D8 | BHALO815 and 816: columns "採番マスタより表示"; BHALO815 更新 = 全件削除後、全件登録 | Copy-paste (the data is 人気業種マスタ / 管理マスタ). Delete-and-reinsert changes every id on each save. | Rows are updated by id; new rows inserted, removed rows deleted. |
| D9 | BHALO812: レベル1/2/3 codes typed by hand; 更新 = delete all rows with the same レベル1・2, then insert | Depends on the numeric codes that already clash (B1). | D10 | 共通仕様 画面遷移: pass the calling screen in 引数パラメータ and return to it | A form-application convention; a web app has URLs and links. | 「もどる」 and post-save redirects go to the list screen; links from a company or school screen open the related job or recruitment screens. |

| D12 | BHALO806 jumps to each registration screen (014–026, 202) for the child tables | Same as D11. | The child tables are editable sections on the member's edit screen. |
| D13 | `src/lib/options.ts` (public wizard) and `db/seed.sql` (選択項目マスタ) used different values, e.g. `Bengali` vs `ベンガル語`, `男性 (Male)` vs `男性` | Values typed in the wizard would not match the master the admin screens use. | The wizard now stores the master's Japanese labels (display text can stay bilingual). |
